<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repository/cache override → store path | Local filesystem configuration selects where the SQLite file would live |
| existing SQLite file → migration runner | Potentially corrupt, tampered, or newer-version local state is parsed by rusqlite |
| private store module → kernel/cache modules | Only typed configuration/status may cross; SQL and raw rusqlite handles must not |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-64-01-01 | Tampering / Elevation | cache path redirected through symlink or escape | mitigate | Reuse `CacheLayout` and `repo_fs` no-symlink ownership; disabled mode does not touch the path. Plan 02 adds open-time verification before SQLite access. |
| T-64-01-02 | Tampering | future schema overwritten by an older binary | mitigate | Compare `PRAGMA user_version` before migration; refuse newer versions and assert sentinel bytes/data remain unchanged. |
| T-64-01-03 | Repudiation | invalid schema silently treated as current | mitigate | Validate the v1 bootstrap invariant and return a typed `InvalidSchema` outcome; dedicated fixture proves refusal. |
| T-64-01-04 | Supply chain | new native SQLite dependency | mitigate | Use the research-locked `rusqlite 0.40.1` with only `bundled`; Cargo.lock and existing dependency gates pin resolution; no ORM/migration helper is added. |
| T-64-01-05 | Information disclosure | SQL/table vocabulary escapes public APIs | mitigate | Store module is private, facade items are `pub(crate)`, and no rusqlite payload appears in any crossing type; Plan 04 adds the outside-consumer leak proof. |
</threat_model>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| validated kernel output → store maintenance | Store runs after facts are validated but must not influence those facts or diagnostics |
| store status → kernel telemetry | Private outcome is recorded without entering public policy output |
| isolated test child environment → benchmark mode | Internal harness selects enabled measurement without creating a supported user contract |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-64-03-01 | Tampering | store state changes confident policy answers | mitigate | Hook runs after validation, reads/persists no facts in Phase 64, and six-mode byte/exit parity test covers ready and failure states. |
| T-64-03-02 | Repudiation | store failure hidden with no internal evidence | mitigate | Typed `StoreStatus` is retained in private `KernelRunReport`; tests assert each failure class while public diagnostics remain unchanged. |
| T-64-03-03 | Denial of Service | disabled mode still opens/checks SQLite on hot path | mitigate | `StoreConfig.enabled` branches before path/open work; full-kernel disabled test asserts no filesystem artifact. |
| T-64-03-04 | Elevation / Information disclosure | provider or rule gains SQL/store access | mitigate | Reuse existing `KernelInput.cache`; do not add store/connection parameters to providers/rules; raw types remain under private module. Plan 04 leak gate enforces. |
| T-64-03-05 | Tampering | benchmark mode env accidentally becomes product behavior | mitigate | Env is read only in `#![cfg(test)]` bench runner/child; normal cache constructors remain disabled; no CLI/config/docs exposure. |
| T-64-03-06 | Repudiation | store size stays hard-coded 0 and hides footprint | mitigate | Enabled isolated measurement reads actual semantic-store directory bytes and asserts >0; disabled remains exactly 0. |
</threat_model>

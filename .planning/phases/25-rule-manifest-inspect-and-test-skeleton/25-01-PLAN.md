<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Macro input -> generated manifest | User-authored rule signatures become trusted manifest metadata used by inspect/test commands. |
| Internal manifest -> public API | Manifest data must not accidentally become an importable SDK type before a deliberate promotion. |
| Rule options -> manifest | Config-derived options may contain custom strings and must be reported deterministically without leaking source text or paths. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-25-01-01 | Spoofing | macro fact-view parsing | mitigate | Keep canonical path and placeholder lifetime validation; reject lookalike paths and aliases exactly as current macro tests do. |
| T-25-01-02 | Tampering | manifest capability rows | mitigate | Derive capabilities from the same typed fact-view parameters used for runtime view construction; do not accept user handwritten capability rows. |
| T-25-01-03 | Information Disclosure | manifest serialization | mitigate | Manifest model excludes source text, absolute paths, temp roots, timestamps, parser ASTs, and run-local IDs. |
| T-25-01-04 | Elevation of Privilege | SDK exports | mitigate | Keep `RuleManifest` and requirement types out of `sdk::prelude` and crate root; expose them only through `sdk::__private` for generated code if needed. |
| T-25-01-05 | Repudiation | deterministic ordering | mitigate | Sort fact-view and capability rows and pin JSON through unit tests. |
</threat_model>

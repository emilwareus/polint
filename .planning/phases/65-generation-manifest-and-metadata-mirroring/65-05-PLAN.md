# Phase 65 Plan 05: R4 Metrics Provider Metadata Mirror

<objective>
Mirror exactly one audited provider family, `polint.metrics`, from canonical
in-memory truth into the private generation store and back without persisting
metric facts or enabling normal-run reuse.

Purpose: Establish the smallest end-to-end provider-metadata proof on top of
the accepted generation lifecycle, run manifest, and sealed outcome boundary:
honest consumed-input identity, atomic publication, exact reopen/match, and
fail-closed tamper handling.

Output: A canonical metrics input/output projection, schema-v4 relational
provider mirror, typed private publication/read/match seam, and focused
identity/migration/rollback/tamper/parity evidence. R5-R6, Phase 65, and
STORE-04/STORE-05/META-01/META-04 remain open.

<interfaces>
Current contracts to preserve and extend narrowly:

- `ProviderManifest` is the static source of provider ID/version, kind,
  declared input/output members, language scope, cache policy, schema members,
  and precision ceiling. The only selected row is `polint.metrics`.
- `ProviderOutcome` is already sealed in static-manifest order with the six
  final states. Only `Succeeded` owns `ProviderOutputIdentity`; legal
  non-success owns typed stage/reason and only `DependencyBlocked` owns exact
  blockers.
- `AnalysisDb` contains source, non-synthetic function, and all three metric
  fact families. Canonical projection must translate transient IDs to
  normalized paths and validate all counts/relationships before identity.
- `derive_requested_metrics_with_cache_stats` currently computes one identity
  path on cold/cache-disabled execution and a LayerKey-dependent path on warm
  writes/hits. Its signature also accepts broad config and upstream syntax
  identities that metrics does not read.
- `LayerKey::metrics_layer_key` has fixed generic slots. R4 may fill
  irrelevant slots with explicit purpose-typed absence and may not redesign
  `LayerKey`, `Digest`, `DependencyIndex`, or another provider key.
- `RunManifest` and its relational codec remain the full run/workspace truth.
  Provider matching is narrower: it authenticates the selected generation and
  workspace but compares the metrics projection without treating broad
  config/rule state as a metrics dependency.
- `SemanticStore::publish_generation` reserves caller-supplied handles and
  `generation::publish_transaction` writes/readbacks the run manifest, marks
  complete, validates, rotates the singleton active pointer, and commits in
  one immediate transaction. R4 extends that transaction; it does not create a
  parallel publication path.
- `AnalysisKernel::run` currently performs only
  `SemanticStore::maintain` after provider truth is sealed. That remains the
  only production store call in the kernel.

    - Test `extracts_go_imports_from_tree_sitter`: single and block imports produce deterministic `ImportFact` values with import aliases stored in `ImportFact.package` when present.
    - Test `extracts_go_functions_methods_calls_and_complexity_from_tree_sitter`: function declarations and method declarations produce `FunctionFact` values with stable names, spans, exported flags, sorted/deduped calls, and parser-backed cyclomatic complexity.

  </behavior>
  <action>
    In `crates/polint-go/src/lib.rs`, replace line-based `extract_imports`, `extract_functions_and_tests`, `function_name`, `find_function_end`, string `calls`, and string `cyclomatic_complexity` usage for declarations with tree-sitter traversal.

    Add helper functions that operate on `tree_sitter::Node` and borrowed source text:
    - `extract_imports(db, file_id, source, root_node)` walks `import_declaration`, `import_spec_list`, and `import_spec` nodes. Store the unquoted import path in `ImportFact.path`. Store an explicit alias/package identifier (`foo`, `.`, or `_`) in `ImportFact.package` when present, otherwise `None`.
    - `extract_functions(db, file_id, source, root_node)` walks `function_declaration` and `method_declaration` nodes in tree order. Function names should remain `Authorize`; method names should be distinguishable as `{Receiver}.{Method}` where receiver strips pointer markers and package qualifiers where practical, for example `Service.Authorize`.
    - `extract_calls(source, body_node)` walks `call_expression` nodes, extracts the function expression text, trims selector calls to a stable text such as `charge` or `log.Printf`, then sorts and dedupes.
    - `go_cyclomatic_complexity(source, body_node)` starts at 1 and increments for parser-backed `if_statement`, ordinary `for_statement`, range loops, switch/select cases/defaults, and boolean `&&`/`||` binary expressions.

    Use `span_from_byte_range` for every `FunctionFact` and `ImportFact` span. Keep `FunctionFact.language = Language::Go`. Keep `is_exported` derived from the function or method name's first letter. Do not add semantic import resolution or graph command changes; `GO-04` import graph support is satisfied by accurate `ImportFact` values feeding the existing `polint-graph` helper.
  </action>

  <action>
    In `crates/polint-go/src/lib.rs`, extend parser-backed function extraction so `_test.go` files identify test entry points named `Test*`, `Benchmark*`, and `Fuzz*` with the expected Go testing signature where practical. Store `FunctionFact.is_test = true` for those functions and push a corresponding `TestFact`.

    Build `TestFact` values from the parsed function body:
    - `name`: the test function name.
    - `span`: the parser-derived function span.
    - `function`: the `FunctionId` returned by `db.push_function`.
    - `subtest_count`: count `call_expression` nodes whose callee text is `t.Run`.
    - `assertion_count`: count common failure/assertion calls (`t.Fatal`, `t.Fatalf`, `t.Error`, `t.Errorf`, `require.*`, `assert.*`) plus simple `if got != want` / `if err == nil` / `if err != nil` error-check conditions.
    - `table_rows`: count practical table-driven rows from composite literal elements inside test function bodies. Keep this heuristic conservative and syntax-based.
    - `evidence_terms`: deterministic sorted/deduped terms from identifiers and string literals useful to later heuristic rules, including `err`, `error`, `invalid`, `denied`, `nil`, `fail`, subtest names, and table-case names where practical.

    Keep the extraction explicitly heuristic in function names/comments where appropriate, but do not use vague diagnostic wording here because `TestFact` stores facts only. Do not claim exact coverage per D-12.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Repository Go source to fact extractor | Untrusted source text drives parser node traversal and fact creation. |
| Go adapter to graph helpers | Import strings become graph node labels in local DOT output. |
| Go adapter to example rules | Heuristic test evidence influences rule diagnostics. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-02-01 | Tampering | import/function/test fact insertion | mitigate | Preserve deterministic tree-order traversal and core insertion order; test exact fact order. |
| T-04-02-02 | Denial of Service | call/evidence extraction | mitigate | Walk the existing tree once per extraction family; avoid repeated full-source cloning and keep sorting/deduping on small fact vectors. |
| T-04-02-03 | Information Disclosure | import graph labels | accept | DOT labels contain only local relative paths and import strings already present in source. |
| T-04-02-04 | Spoofing | test evidence heuristics | mitigate | Name helpers/tests as heuristic and avoid wording that claims exact test coverage. |
</threat_model>

# W1.3 — Rule-execution telemetry

**Tier:** 🟡 → 🟢 once this spec is read. **Precondition:** M0.A green.

---

## Goal

Make "my rule matched nothing" diagnosable in one command. Today a rule that found nothing is
indistinguishable, from the output alone, from a rule that was never planned or whose file scope
excluded everything.

## Why

`AiFriendlySummary` (`diagnostics/mod.rs:1075-1081`) is:

```rust
pub(crate) struct AiFriendlySummary {
    pub(crate) total_diagnostics: usize,
    pub(crate) rules_triggered: usize,        // == by_rule.len()
    pub(crate) by_severity: BTreeMap<String, usize>,
    pub(crate) by_rule: Vec<AiFriendlyRuleSummary>,
    pub(crate) examples_limit: usize,
}
```

`rules_triggered` is the count of rules that produced ≥ 1 diagnostic. **Rules that produced zero
appear nowhere.** There is no `rules_evaluated`, no zero-finding list, no per-rule scope count.

This is the worst failure mode in the agent authoring loop, and it is cheap to close.

---

## Design decisions

### D1 — The new row

```rust
pub(crate) struct RuleExecutionRow {
    pub(crate) rule_id: String,
    pub(crate) planned: bool,              // survived capability planning
    pub(crate) capabilities_ok: bool,      // all requested capabilities supported here
    pub(crate) files_in_scope: usize,      // files matching this rule's scope AFTER filtering
    pub(crate) diagnostics_emitted: usize,
    pub(crate) skipped_reason: Option<String>,  // set iff !planned || !capabilities_ok
}
```

Add `rules: Vec<RuleExecutionRow>` to `AiFriendlySummary`. **Keep `rules_triggered` exactly as it is** —
it is an existing public JSON contract. Add, do not redefine.

### D2 — `files_in_scope` is the load-bearing field, and it must be honest

This is the field that answers "why did my rule see nothing," so it must be the count **after** every
filter that can exclude a file: the rule's `files` glob, `allow_files`/`deny_files`, and the kernel's
rule-scope globset (`AnalysisKernel::rule_scope_globset`).

**If you cannot compute the post-filter count cheaply, emit `None` rather than a pre-filter count.** A
wrong number here is worse than no number — it will send an agent down the wrong path with confidence.

### D3 — Every registered rule gets a row, including ones that never ran

Rows come from the **rule registry**, not from the diagnostics. A rule dropped during capability
planning must still produce a row with `planned: false` and a `skipped_reason` — that is precisely the
case being diagnosed. Source the reason from the existing `polint/capability` diagnostic text
(`analysis_plan.rs:539-579`) rather than writing new wording.

### D4 — JSON only; the text renderer stays quiet

Emit in `--format ai-friendly` and `--format json`. **Do not print zero-finding rules in the human
text renderer** — a repo with 200 rules and 3 findings would print 197 lines of noise and users would
disable the format.

### D5 — This changes golden output

The summary object gains a field. Ships as a behaviour PR with regenerated goldens, per HANDOFF §2
rule 2. The diagnostic set must not change.

---

## Implementation steps

1. **Add `RuleExecutionRow` and the `rules` field**; populate `rule_id`, `planned`,
   `capabilities_ok`, `diagnostics_emitted`, `skipped_reason`. Leave `files_in_scope` as `None`.
2. **Add `files_in_scope`** with the post-filter count (D2), or leave `None` and escalate if the
   filters cannot be composed cheaply.
3. **Regenerate goldens** in a separate PR.
4. **Update the JSON schema** under `docs/schemas/` and the skill text — `cli/skill.rs` is the source
   of truth; W1.9 adds the byte-equality test.

## Acceptance

```rust
#[test]
fn a_rule_that_matches_nothing_appears_in_the_summary() {
    // Register a rule whose predicate never matches.
    // Assert: a row exists, planned = true, capabilities_ok = true,
    //         files_in_scope > 0, diagnostics_emitted = 0.
}

#[test]
fn a_rule_dropped_by_capability_planning_reports_why() {
    // Register a rule requesting an unsupported capability.
    // Assert: row exists, planned = false, skipped_reason is Some and non-empty.
}

#[test]
fn a_rule_whose_scope_excludes_everything_reports_zero_files() {
    // Register a rule with a files glob matching nothing.
    // Assert: files_in_scope == 0.
}
```

The third test is the one that matters most — it is the case that is currently undiagnosable.

Plus: `jq '.summary.rules[] | select(.diagnostics_emitted == 0)' .polint/output/latest.json` returns
the silent rules on a real run.

## Anti-goals

Do not change or redefine `rules_triggered`. Do not add per-rule timing here (that is W0.A4's
concern and belongs in the cost record, not the diagnostic report). Do not print zero-finding rules in
text output. Do not report a pre-filter `files_in_scope`.

## Escalate if

The scope filters cannot be composed to give an honest post-filter count · adding the field breaks the
`docs/schemas/` closed-object validation in a way you cannot resolve by updating the schema · the
diagnostic set changes.

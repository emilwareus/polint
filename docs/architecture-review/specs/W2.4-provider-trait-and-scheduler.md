# W2.4 — `Provider` trait and manifest-driven scheduler

**Tier:** 🟡 → 🟢 once this spec is read. **Precondition:** W2.2 (`core/mod.rs` split), M0.A green.

---

## Goal

Delete the 877-line hand-written `AnalysisKernel::run` and replace it with a scheduler that executes
the provider DAG already declared in `PROVIDER_MANIFESTS`.

## The fact that makes this safe

**The 23 manifest entries appear in exactly the same order as the 23 `provider_output_for` calls in
`run()`.** Verify yourself:

```bash
rg -o 'id: "[a-z0-9._]+"' crates/polint/src/analysis_kernel/provider.rs | sed 's/id: //' | head -23
rg -A1 'provider_output_for(_with_optional_digest)?\($' crates/polint/src/analysis_kernel/mod.rs | rg -o '"[a-z0-9._]+"'
```

Both produce: `polint.source`, `polint.go.syntax`, `polint.ts.syntax`, `polint.module_graph`,
`polint.symbol_graph`, `polint.module_topology`, `polint semantic-MIR provider`, `polint.cfg`, `polint.calls`,
`polint.go.semantic`, `polint.identity`, `polint.abstract_domains`, `polint.direct_summaries`,
`polint.entrypoints`, `polint.reachability`, `polint.extensions`, `polint.type_value_alias`,
`polint.semantic_graph`, `polint.solver`, `polint.refined_calls`, `polint.data_flow`,
`polint.evidence`, `polint.metrics`.

**You are not discovering a new order. You are proving the declared data reproduces the existing
one.** That converts this from a redesign into a verification exercise.

## Design decisions (do not deviate; escalate instead)

### D1 — The trait

```rust
pub(crate) trait Provider: Send + Sync {
    fn manifest(&self) -> &'static ProviderManifest;
    fn run(&self, ctx: &mut ProviderCtx<'_>) -> ProviderRunResult;
}
```

`ProviderManifest` is used **verbatim** as it exists at `analysis_kernel/provider.rs:2-11`. Do not
add, remove, or rename a field in this task.

### D2 — `ProviderRunResult` is the existing `ProviderAnalysisResult`, deduplicated

`ProviderAnalysisResult` is currently declared **twice, byte-identically**, at `go/adapter.rs:72-76`
and `ts/adapter.rs:104-108`:

```rust
pub(crate) struct ProviderAnalysisResult {
    pub(crate) diagnostics: Vec<Diagnostic>,
    pub(crate) cache_stats: CacheStats,
    pub(crate) output_digest: Option<Digest>,
}
```

Move it to one place (`analysis_kernel/provider.rs`), rename to `ProviderRunResult`, delete both
copies. **This deduplication is step 1 and ships as its own PR.**

### D3 — `ProviderCtx` carries what `run()` currently threads by hand

```rust
pub(crate) struct ProviderCtx<'a> {
    pub(crate) db: &'a mut AnalysisDb,
    pub(crate) cache: &'a Cache,
    pub(crate) config_digest: &'a str,
    pub(crate) rule_digest: &'a str,
    pub(crate) plan: &'a AnalysisPlan,
    pub(crate) parallel: bool,
    /// Output digests of already-run providers, keyed by provider id. Replaces the
    /// ~30-line `_dependency_output_digest` unwrap block repeated 20× in `run()`.
    pub(crate) upstream_digests: &'a BTreeMap<&'static str, Digest>,
}
```

### D4 — Scheduling is a topological sort with a deterministic tie-break

Build a DAG: provider P depends on provider Q if any string in `P.inputs` appears in `Q.outputs`.
Topologically sort. **Break ties by manifest declaration index**, not by id, not by name. This is what
makes the sort reproduce today's order exactly and makes output deterministic.

### D5 — Gating stays capability-based, but derived instead of hand-maintained

The six booleans (`run_cross_file_analysis`, `run_semantic_pipeline`, `run_cfg_call_pipeline`,
`run_full_refinement_pipeline`, `run_data_flow_pipeline`, `compact_domain_materialization`) and their
five `*_TRIGGER_CAPABILITIES` constants are replaced by:

1. Map requested capabilities → the providers whose `outputs` supply them.
2. Take the transitive closure over the dependency edges.
3. Run exactly that set, in topological order.

**Keep the constants in the tree until step 5 proves equivalence, then delete them in one PR.**

### D6 — What is explicitly NOT in this task

- **No parallel execution.** Sequential, in topological order. Parallelising the DAG is a later task.
- **No change to any provider's internals.** Each `impl Provider` wraps the existing function call.
- **No change to `AnalysisDb`.** That is W2.5.
- **No new provider.** No removed provider.
- **No manifest data changes** unless step 4 proves a declared input/output is wrong — and then that
  is its own PR with the correction justified in prose.

## Implementation steps — one PR each

**Step 1 — Deduplicate `ProviderAnalysisResult`.**
Move to `analysis_kernel/provider.rs` as `ProviderRunResult`; update the two adapters. No behaviour
change. *Acceptance:* full suite green, golden output byte-identical.

**Step 2 — Add the trait and `ProviderCtx`; implement for 2 providers only.**
Pick `polint.source` and `polint.go.syntax`. Call the new impls from `run()` in place of the inline
code; leave the other 21 stages untouched. *Acceptance:* golden output byte-identical.

**Step 3 — Implement `Provider` for the remaining 21.** Split across several PRs, ≤ 5 providers each,
staying inside the line budget. `run()` still calls them in hardcoded order. *Acceptance after each:*
golden output byte-identical.

**Step 4 — Build the DAG and assert it reproduces the order. No execution change yet.**
Add `fn scheduled_order() -> Vec<&'static str>` plus a test:

```rust
#[test]
fn topological_order_matches_declared_manifest_order() {
    let scheduled = scheduled_order();
    let declared: Vec<&str> = provider_manifests().iter().map(|m| m.id).collect();
    assert_eq!(scheduled, declared);
}
```

**If this test fails, STOP and escalate.** It means either a manifest's `inputs`/`outputs` are wrong
or the current execution order contains an accident. Both are findings worth a human decision. Do not
"fix" it by editing the expected value or by special-casing the sort.

**Step 5 — Prove capability-closure equivalence with the boolean gates.**
For every subset of capabilities the CLI can request, assert the derived provider set equals the set
the booleans would have enabled. Table-driven test over the capability list at
`analysis_kernel/mod.rs:30-60`. *Acceptance:* equivalence holds for every case.

**Step 6 — Switch `run()` to drive the scheduler; delete the dead code.**
`run()` becomes roughly:

```rust
let order = scheduled_order_for(plan);
let mut upstream = BTreeMap::new();
for provider in order {
    let result = provider.run(&mut ctx);
    if let Some(d) = result.output_digest { upstream.insert(provider.manifest().id, d); }
    diagnostics.extend(result.diagnostics);
    provider_outputs.push(provider_output_for(...));
}
```

Delete in the same PR: the six booleans, the five `*_TRIGGER_CAPABILITIES` constants, both duplicated
provider-order assertions, and all 20 copies of the `_dependency_output_digest` block.

## Anti-goals

Do not introduce `dyn` dispatch on the hot per-fact path — providers are coarse-grained; a `Box<dyn
Provider>` per *stage* is fine, per *fact* is not. Do not make `Provider` public. Do not add async. Do
not "improve" a provider while wrapping it. Do not reorder providers to make the sort tidier.

## Escalate if

The step-4 order test fails · a provider's real inputs contradict its manifest · a provider needs
state not in `ProviderCtx` · any step changes golden output.

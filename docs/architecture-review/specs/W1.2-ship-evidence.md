# W1.2 — Ship structured evidence

**Tier:** 🟡 → 🟢 once this spec is read. **Precondition:** M0.A green (this task *intentionally*
changes golden output — the goldens must exist first so the change is visible and reviewable).

---

## Goal

Stop deleting the provenance the engine already computes. Make `evidence_v1` reach users for the query
families that already produce it.

## Why

`crates/polint/src/analysis/evidence/` is **4,335 lines** implementing exactly the provenance model
the product needs: nodes bound to file/function/MIR-op/CFG-node/place/symbol/call-site, bundles keyed
by `diagnostic_stable_key` with selected paths and a `replay_key`, unknown reasons
(`DynamicCall`, `UnsupportedEdge`, `SetupMissing`, `BudgetExceeded`, `OpaqueSummary`), omitted-region
reasons, and a renderer with explicit `total_*` vs `rendered_*` budgets.

Users see none of it. Three independent reasons:

1. `Diagnostic::with_structured_evidence_v1` (`diagnostics/mod.rs:936-938`) has five call sites, **all
   after `#[cfg(test)] mod tests` at line 2303**.
2. It is **actively erased** at the rule-host boundary — `diagnostics/mod.rs:1131-1142`:
   ```rust
   pub(crate) fn diagnostics_from_public_json_report(s: &str) -> Result<Vec<Diagnostic>, _> {
       let mut diagnostics = diagnostics_from_json_report(s)?;
       for diagnostic in &mut diagnostics {
           diagnostic.evidence_v1 = None;
           diagnostic.evidence_bundle = None;
       }
       Ok(diagnostics)
   }
   ```
   Every repo-local rule returns through this function.
3. The fields are `pub(crate)` on the serialized struct (`diagnostics/mod.rs:775-778`).

---

## Design decisions

### D1 — Scope: policy-query families only

Ship evidence **only** for diagnostics produced through `sdk/policy.rs` (`FlowQuery`, `ReachQuery`,
`GuardQuery`, `LifecycleQuery`). Those already carry engine-derived provenance.

**Do not attach evidence to hand-written rule diagnostics.** A rule author calling
`Diagnostic::error(...)` has no engine-derived path, and synthesising one would be a fabricated
provenance claim — the exact opposite of this feature's purpose.

### D2 — `StructuredEvidenceV1` becomes public, unchanged internally

It is already a validated JSON wrapper (`diagnostics/mod.rs:142-155`):

```rust
pub(crate) struct StructuredEvidenceV1 { value: serde_json::Value }
```

Make it `pub`, keep the field private, keep `try_from_value` as the only constructor so the validator
cannot be bypassed. Add it and the `evidence_v1` field to the SDK prelude; update the leak-gate
allowlist count deliberately, in the same PR, with the change stated in the PR description.

### D3 — Replace the blanket strip with a validated pass-through

`diagnostics_from_public_json_report` must stop nulling `evidence_v1`. But it is a **trust boundary** —
that JSON comes from a child process compiled from user code.

- `evidence_v1`: **validate and keep.** Run `validate_structured_evidence_v1` on the incoming value;
  on failure drop the field and emit an internal diagnostic. Never propagate unvalidated JSON.
- `evidence_bundle`: **keep stripping.** It is `#[serde(skip)]` and holds an internal store reference
  meaningless across a process boundary.

### D4 — Bounded by default; the budgets already exist

The renderer's defaults (`evidence/render.rs:28-37`) are `max_paths: 5`, `max_edges_per_path: 96`,
`max_unknowns: 32`, `max_omitted_regions: 32`. **Use them as-is.** The envelope already reports
`total_*` vs `rendered_*` so truncation is visible rather than silent.

Evidence must not appear in the human-readable text renderer by default — it would drown the terminal.
JSON and SARIF only.

### D5 — This changes golden output, deliberately

Diagnostics gain an `evidence_v1` field. That is the point.

Per HANDOFF §2 rule 2, this ships as a **behaviour PR**: the golden regeneration is the deliverable and
the PR description must state that diagnostics gain evidence, that the diagnostic *set* is unchanged,
and that only the added field differs. **Any change to which diagnostics are reported means something
else broke — report ESCALATE.**

## Implementation steps

1. **Make `StructuredEvidenceV1` public; update the leak-gate allowlist.** No behaviour change yet.
2. **Attach evidence in the policy-query path** — `sdk/policy.rs:152-165` already auto-attaches five
   flat header fields; add the structured bundle alongside them. Keep the flat fields for compatibility.
3. **Replace the strip with validated pass-through** (D3).
4. **Regenerate goldens** as a separate, clearly-described PR.
5. **Add the coverage assertion** (below).

## Acceptance

```rust
#[test]
fn policy_query_findings_carry_replayable_evidence() {
    // Run a policy-query rule over a fixture with a known multi-hop flow.
    // Assert: evidence_v1 present; path non-empty; replay_key present;
    //         unknowns array present (may be empty); limits block present.
}

#[test]
fn malformed_evidence_from_a_rule_host_is_dropped_not_propagated() {
    // Feed a report whose evidence_v1 fails validation.
    // Assert: field absent, an internal diagnostic is emitted, no panic.
}
```

Plus:
```bash
cargo test -p polint --test public_surface_leak --locked   # allowlist updated deliberately
cargo test -p polint --test golden --locked   # diff is ADDED FIELDS ONLY
```

**Metric: >90% of policy-query findings carry an evidence path.** Measure it; do not assume it.

## Anti-goals

Do not attach evidence to hand-authored rule diagnostics (D1). Do not raise the render budgets. Do not
add evidence to the text renderer. Do not make `EvidenceStore`, `EvidenceNodeFact`, or any
`analysis/evidence/` internal type public — only the rendered `evidence_v1` envelope crosses the
boundary. Do not skip validation on the trust boundary.

## Escalate if

The set of reported diagnostics changes (not just their fields) · validation rejects
engine-produced evidence · the leak-gate delta is larger than the fields you intended to add.

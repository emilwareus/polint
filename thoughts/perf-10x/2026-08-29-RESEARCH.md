# `polint check` — where the warm and cold seconds actually go

Research pass for the perf/scan-10x mission. polint 0.3.0 (`13e53f35`, == tag `v0.3.0`),
8-core AMD EPYC / 15 GB RAM, Go 1.27.0, rustc 1.95 & 1.97.1.
Benchmark repos: `/workspace/benchmark-plinty` (68 `[[rules.config]]` entries over 48 rule
source files; **77 registered check rules** execute) and `/workspace/benchmark-devloupe`
(25 `[[rules.config]]` entries over 26 source files; **20 check rules** execute — the five
`review/*` rules are `RuleKind::Review` and are skipped by `check`).

**Every number below was measured in this session.** Method, commands, and raw output are
in the appendix. All temporary instrumentation has been reverted; the working tree is clean
apart from this `thoughts/` directory.

---

## 0. Executive summary

Warm `polint check` is not dominated by parsing, by the cache, or by rule execution. It is
dominated by **two accidentally quadratic / redundant bookkeeping paths that run on every
scan regardless of cache state**:

| # | Cost centre | plinty warm | devloupe warm | Root cause |
|---|---|---|---|---|
| 1 | `CanonicalGoSyntaxOutput::from_db` (the Go-syntax provider **output digest**) | **9.67 s — 69.8 %** | **3.25 s — 29.9 %** | `canonical_span()` calls `source.source.lines().count()` **once per Go fact**. 128 234 facts → **11.69 GB** of source re-scanned on plinty; 188 103 facts → **5.04 GB** on devloupe. |
| 2 | `AnalysisPlan::rule_execution_rows` (report metadata) | **1.64 s — 11.8 %** | **1.54 s — 14.1 %** | `O(rules × files)` glob matching where each call clones a memoized `GlobMatcher` (which clones `String`s) and `format!("./{path}")`-allocates. 213 k calls @ 7.7 µs (plinty), 84 k @ 18.4 µs (devloupe). |
| 3 | Syntax-layer cache **hit** path | 0.94 s + 0.35 s | 1.32 s + 0.69 s | Each hit deserialises the layer blob **twice** and re-**serialises** it a third time to recompute a digest it already has; then `restore_file_facts` pays per-fact stable-key interning + payload digest. |
| 4 | Metrics layer permanently missing (devloupe only) | — | 1.17 s + 20.6 MB rewritten | The metrics layer **manifest is 5.73 MB**, above `LAYER_CACHE_MANIFEST_MAX_BYTES = 4 MiB`, so the read fails, evicts, and recomputes **on every run, forever**. |
| 5 | Rule execution | 0.58 s | 1.78 s | Rayon-parallel, but wall time == the single slowest rule in both repos (551 ms / 1702 ms). Adding cores cannot help. |

To convert hypotheses into measured impact I built the three cheapest fixes behind an env
gate and A/B-ed them in one binary against the same caches:

| repo | tier | v0.3.0 | prototype | speedup | output |
|---|---|---|---|---|---|
| plinty | warm | 13.59 s | **2.68 s** | **5.07×** | byte-identical |
| plinty | cold | 22.05 s | **11.15 s** | 1.98× | byte-identical |
| devloupe | warm | 10.57 s | **5.50 s** | 1.92× | byte-identical |
| devloupe | cold | 12.29 s | **7.33 s** | 1.68× | byte-identical |

plinty warm already clears the mission target (≤ 3.1 s) from three behaviour-preserving
changes. devloupe warm and both cold tiers need the second wave described in §9.

## 1. Anatomy of a run, and where measurement has to happen

`polint check` in a repo that has `.polint/rules` **does no analysis itself**. It shells out:

```
crates/polint/src/cli/mod.rs:3418  check()
  -> :3872 discover_local_rule_hosts()          # .polint/rules/Cargo.toml exists
  -> :3949 check_local_rule_hosts()
       -> :4252 run_local_rule_host_kind()
            cargo run --quiet --release --manifest-path .polint/rules/Cargo.toml
              -- check --format json --fail-on none --ignore-comments true --kind check
            env POLINT_CACHE_DIR=<repo>/.polint/cache
            env CARGO_TARGET_DIR=<rules target>
       -> parse the child's JSON report, render, exit
```

The child (`polint::runner::run_cli`, `crates/polint/src/runner/mod.rs:380 analyze_and_run`)
owns config load, the analysis plan, the kernel, the providers, the cache, and rule
execution. **The child's stderr is captured by `Command::output()` and thrown away unless
it fails**, which is why `RUST_LOG=polint::kernel=info` produces nothing when you run
`polint check` — you have to run the host binary directly to see it.

Measured split of the outer wrapper (3 runs each, medians):

| repo | `polint check` (outer) | rule host run directly | wrapper overhead |
|---|---|---|---|
| plinty | 13.817 s | 13.710 s | **0.11 s (0.8 %)** |
| devloupe | 10.903 s | 10.434 s | **0.47 s (4.3 %)** |

devloupe's wrapper cost is higher because it parses a 443 KB JSON report, reads sources for
492 diagnostics and renders 6.7 MB of human output. The `cargo run` no-op itself is ~150 ms
(prior-art measurement, §8). At today's 11-14 s totals the wrapper is noise; **after the
fixes it is 4 %–9 %**, so it earns a hypothesis of its own (H8).

### Instrumentation rig

The rule hosts link `polint` from crates.io / git tag, not from this worktree, so the only
way to see inside them is to build a host against a path dependency. I copied each repo's
`.polint/rules` to `/tmp/perf10x/rules-<repo>`, repointed the `polint` dependency at
`/workspace/benchmark-polint/crates/polint`, and built with each repo's own toolchain
(plinty 1.97.1, devloupe 1.95).

**Rig validation:** the un-instrumented path-dep host produced a **byte-identical** JSON
report to `/workspace/bench-polint-results/bin/polint`'s child on both repos, and so did
every instrumented and prototype build. Probes are `eprintln!` behind one cached
`POLINT_PERF` env lookup, so stdout is untouched.

`perf`, `strace`, `ltrace` and `gdb` are all absent from this container and
`perf_event_paranoid=4`, so sampling profilers were not an option; all attribution below is
explicit timing instrumentation.

The deep semantic stack (`semantic_mir`, `cfg`, `calls`, `go.semantic`, `identity`,
`abstract_domains`, `direct_summaries`, `entrypoints`, `reachability`, `extensions`,
`type_value_alias`, `semantic_graph`, `solver`, `refined_calls`, `data_flow`, `evidence`,
`module_topology`) is **switched off for both packs** — no rule in either repo requests
`calls`, `control_flow`, or `dataflow`. The capability gate works; the cost is elsewhere.

The single most important structural fact: **`provider.digest.*` is a bigger cost centre
than every provider combined.** It is computed in the kernel loop *after* the provider
returns (`analysis_kernel/mod.rs`, the `match provider_id { "polint.go.syntax" => ...
CanonicalGoSyntaxOutput::from_db(db, &parser_diagnostics)... }` block) and its only consumer
is the run-report identity record. Because the log line `"phase: go.syntax done"` is emitted
*before* that block, the naive reading of the tracing output attributes 9.7 s of Go-digest
work to the TypeScript provider — which is exactly the wrong conclusion this research
started from.

## 6. The cache: contents, shape, and what a warm run pays for it

### 6.1 Layout and size

`.polint/cache/` has two independent stores:

| store | plinty | devloupe | shape |
|---|---|---|---|
| `analysis/` — **per-file** facts | 47 MB, 2 764 JSON files | 71 MB, 4 179 files | one uncompressed JSON per source file: `{"schema":"go-facts-v2","diagnostics":[],"facts":{...}}` |
| `layers/blobs` + `layers/manifests` — **per-provider layer** | 42 MB (Go 31.7 MB + TS 11.4 MB) + 0.4 MB manifests | 89 MB (Go 45.3 MB + TS 20.2 MB + metrics 20.6 MB) + 6.4 MB manifests | one blob per provider covering all files, plus a manifest carrying one `input_digest` per file |
| **total** | **88 MB** | **159 MB** | |

The two stores hold **the same facts twice**. The per-file store is only consulted when the
layer key misses (`analyze_go_source_file`, `go/adapter.rs:454`), i.e. on the cold tier, and
is written on every cold run. Fact counts: plinty Go 128 234 / TS 53 448; devloupe Go
188 103 / TS 91 788.

### 6.2 What a warm layer hit costs, step by step (measured)

`analysis_kernel/incremental/layer_cache.rs:275 read_payload_bytes_validated` →
`go/adapter.rs:124` / `ts/adapter.rs:147`:

1. read + parse the manifest (146 KB TS / 295 KB Go), clone+sort+dedup its dependency vector and compare — **~2 ms**
2. read the blob — 16 ms (Go 31.7 MB) / 7 ms (TS)
3. `payload_digest_for_bytes`: UTF-8 validate + byte-at-a-time FNV over the whole blob — **42 ms / 15 ms** (≈ 750 MB/s)
4. validator: **full `serde_json::from_slice` of the blob** — 126 ms / 46 ms
5. validator: `*_syntax_output_digest_for_payload` → **`serde_json::to_vec` of the whole payload again** + FNV — 103 ms / 37 ms
6. caller: **`serde_json::from_slice` of the same blob a second time** — 112 ms / 41 ms
7. `restore_syntax_layer_payload` → `AnalysisDb::restore_file_facts` per file — **510 ms / 191 ms**

Steps 4-6 are 341 ms (Go) / 124 ms (TS) on plinty and 514 ms / 228 ms on devloupe of pure
redundancy: the blob is materialised three times to answer a question the manifest already
answered (step 3 verified `payload_digest == manifest.payload_digest`, and the output digest
is a pure function of the payload digest).

Step 7 is per-fact metadata construction: every `push_function` / `push_import` /
`push_string_literal` / … in `core/db.rs:723+` calls `*_metadata()`, which builds 4-6 fresh
`String`s (`path_for()` clones the relative path, `language_label().to_string()`,
`fact.value.clone()` — the whole literal — and a `format!` span), interns a stable key
through an `Arc<Mutex<HashMap<Arc<str>, _>>>` (two lock round-trips per fact: `intern` +
`resolve`), sorts the parts, and FNV-hashes them into another `String`. At 128 234 facts
that is ~4 µs/fact.

### 6.3 devloupe's metrics layer can never be reused

`LAYER_CACHE_MANIFEST_MAX_BYTES = 4 * 1_048_576` (`layer_cache.rs:26`), and
`read_file_with_limit` **errors** (`RepoFileReadError::TooLarge`) rather than truncating
(`repo_fs.rs:213`). devloupe's metrics manifest is **5 731 391 bytes** — because
`metrics_layer_dependency_edges` emits one `DependencyEdge` per source *and one per
function* (`metrics.rs:137`). So every run:

- `read_json_validated` → manifest over the limit → `evict_file(manifest)` → **Miss**
  (probe: `metrics.read_status = 2` on every baseline run)
- recompute metrics (678 ms), rebuild dependency edges (60 ms), rewrite a 20.6 MB blob and
  a 5.7 MB manifest (186 ms)

Verified by file size, by `metrics.read_status`, by mtime (`95ba3e1b62fde884.json` is
rewritten on every run), and finally by raising the limit to 64 MiB in the prototype, which
flipped `metrics.read_status` to `1` (Hit).

### 6.4 Two cache-key gaps worth recording

**(a) Parser identity is declared but not keyed.** `go_syntax_projection.rs:21` pins
`GO_PARSER_BACKEND = "tree-sitter-0.26.8"` and `GO_PARSER_GRAMMAR = "tree-sitter-go-0.25.0"`
as the parser contract, but `go_syntax_layer_key` (`go/adapter.rs:240`) derives
`toolchain_digest` from `env!("CARGO_PKG_VERSION")` alone. `FileCacheKeyParts`
(`analysis_api/cache_api.rs:10`) carries no version component at all — only path, content
hash, config hash, rule hash, plan hash, and a schema string.

I hit this empirically: my instrumented devloupe host resolved `tree-sitter 0.26.13` (I had
dropped `Cargo.lock`) while the benchmark host's lock pins `0.26.8`. Same polint version,
same content hash, **different facts**: `core/internal/ingest/domain/integration/linear/generated_examples.go`
yields 80 functions under 0.26.8 and 93 under 0.26.13, which is a 492 vs 493 diagnostic
difference. Under today's keys, a `cargo update` of the tree-sitter runtime inside one
polint version would silently reuse facts produced by the old grammar.

**(b) Benchmark hygiene consequence.** Because of the same effect, a `.polint/cache`
produced by one rule-host build is not necessarily equivalent to one produced by another.
For the 10× work this means: **compare warm-vs-warm and cold-vs-cold against the same
baseline binary and the same cache provenance; do not compare a warm run to a cold run and
call a difference a regression.** (Both benchmark repos' caches are byte-for-byte unchanged
by this research — verified at the end.)

## 7. Parallelism: what is parallel, what is serial, and what the critical path is

| stage | parallel? | mechanism |
|---|---|---|
| file discovery (`ignore` walk) | **no** — single-threaded `WalkBuilder::build()` iterator | `fs/mod.rs:44` |
| source reads | yes | `discovered.into_par_iter()` (`fs/mod.rs:141`) |
| `AnalysisDb::add_file` + content hashing | **no** — sequential loop | `fs/mod.rs:153` |
| Go / TS parsing (cold) | yes | `files.par_iter()` in `parse_*_syntax_layer_payload` |
| layer-cache validate / deserialise / digest | **no** | single-threaded on the whole blob |
| `restore_file_facts` | **no** — sequential, and serialised anyway by the stable-key `Mutex` | `go/adapter.rs:344`, `core/db.rs:3682` |
| `CanonicalGoSyntaxOutput::from_db` | **no** — six sequential family loops | `go_syntax_projection.rs:136` |
| provider scheduling | **no** by design — topological order, one at a time | `analysis_kernel/mod.rs:139` |
| `rule_execution_rows` | **no** — sequential `.iter().map()` | `analysis_plan.rs:227` |
| rule execution | yes | `rules.par_iter()` (`core/rule.rs:360`) |

Rule-execution parallel efficiency, measured with `RUST_LOG=polint::rules=info`:

| repo | rules | Σ per-rule CPU ms | wall ms | speedup | slowest single rule |
|---|---:|---:|---:|---:|---|
| plinty | 77 | 1 729 | 553 | 3.1× | `plint/backend-runtime-facades` — **551 ms** |
| devloupe | 20 | 7 438 | 1 731 | 4.3× | `local/code-health-metrics` — **1 702 ms** |

In both repos **wall ≈ the single slowest rule**, so rule execution is critical-path bound,
not throughput bound. More cores buy nothing; only making individual rules cheaper does. The
top rules in each pack are the ones that iterate every file/fact and call
`sdk::scope::file_in_scope` per row — the same memoised-glob path as H2.

Only two stages use more than one core at all: `fs.read_parallel` (23 / 32 ms) and rule
execution (553 / 1 731 ms wall). Everything else is single-threaded, so **95.8 % of plinty's
warm wall and 83.8 % of devloupe's runs on one core** — which is why the wins in §10 come
from removing work rather than from adding threads.

`research/code-preserving-rule-build/FINAL-REPORT.md` is the design answer and is **not
implemented in 0.3.0** — the rule packs still depend on the full `polint` crate and

recommendations, in the order it ranks them: split `polint-sdk` / `polint-engine`; move fact
production into the prebuilt host behind a fact-snapshot protocol; **stop spawning cargo when
nothing changed** (fingerprint rule sources + manifest + SDK version + `rustc -vV`); vendor
the SDK and build `--offline --locked`; only then consider prebuilt rlibs or WASM.

**Safe, behaviour-preserving subset available today:** item 3 alone (H8 below). Items 1-2
are the 0.3.x→0.4 architecture change and are out of scope for a byte-identical
optimisation pass.

`3c0f4dfa` / `14bbaac4` already split the CI cache so `rules-target` is keyed on compiler
inputs (OS/arch, resolved toolchain, flags, manifests, lockfiles) rather than rule sources,
and prunes each rule package's own output before saving — so CI ice-cold is already
addressed for GitHub Actions users. Nothing equivalent exists for local runs.

## 9. Optimization hypotheses

Impact columns marked **[measured]** come from the A/B prototype in §10; the rest are
estimates derived from the probe data. "Risk" is the risk to byte-identical output.

### H1 — Hoist the per-fact `lines().count()` in `CanonicalGoSyntaxOutput::from_db` **[measured]**

`canonical_span()` (`go_syntax_projection.rs:452`) recomputes `source.source.lines().count()`
for every fact in the file. Measured: **11.69 GB** (plinty) / **5.04 GB** (devloupe) of source
re-scanned per run. Compute the line count once per `FileId` in `GoContext`.

- **Impact [measured]: plinty 9 670 ms → 191 ms (−9.48 s, −68 % of warm wall). devloupe 3 251 ms → 280 ms (−2.97 s, −27 %).**
- Risk: **very low.** `lines().count()` is a pure function of the source; the memo returns the identical value. Output verified byte-identical.
- Verify: run the golden corpus; `cmp` the JSON report warm and cold on both benchmark repos against a v0.3.0 baseline capture; assert `SPAN_BYTES == 0` growth in a unit test.

### H2 — Make `sdk::scope::glob_matches` allocation-free on the hot path **[measured]**

`cached_matcher()` (`sdk/scope.rs:51`) returns a **cloned** `GlobMatcher` (cloning the inner
`Glob`'s `String`s) on every call, then `glob_matches` allocates `format!("./{value}")` for
every non-match. Called `rules × files` times from `rule_execution_rows`, and — per its own
doc comment — "once per fact row" from inside rules. Hold the `RwLock` read guard and match
against a borrowed matcher; reuse a thread-local buffer for the `./` variant.

- **Impact [measured]: `rule_execution_rows` plinty 1 635 → 32 ms, devloupe 1 539 → 30 ms (−1.5 s each). Rule execution also fell on devloupe: 1 784 → 1 201 ms (−0.58 s).**
- Risk: **low.** Same matcher, same call order, same short-circuit. Output verified byte-identical.
- Verify: property test `glob_matches_borrowed(p, v) == glob_matches_old(p, v)` over the union of every `files`/`allow_files` pattern in the corpus × every corpus path; golden corpus.

### H3 — Raise (or eliminate) the layer-cache manifest ceiling **[measured]**

The 4 MiB `LAYER_CACHE_MANIFEST_MAX_BYTES` makes devloupe's 5.73 MB metrics manifest
permanently unreadable. Either raise the ceiling to match `LAYER_CACHE_PAYLOAD_MAX_BYTES`
(64 MiB), or stop emitting one dependency edge per function (a single digest over the sorted
function digests carries the same invalidation signal at 1/10⁴ the size).

- **Impact [measured]: devloupe `polint.metrics` 1 167 → ~660 ms of *read* work today (`metrics.read_status` 2 → 1), and it stops rewriting 26 MB per run.** With the edge-shrinking variant the read cost collapses too (the 514 ms `metrics.read_layer` in the prototype is dominated by parsing that 5.7 MB manifest and validating a 20 MB payload).
- Risk: **low** for the ceiling change (it only lets an existing, digest-verified manifest be read). **Medium** for shrinking the dependency edges — it changes the manifest schema and invalidates existing metrics layers once.
- Verify: assert `metrics.read_status == Hit` on the second run of a fixture; golden corpus; a regression test that a layer whose manifest exceeds the old ceiling still round-trips.

### H4 — Read the layer blob once (drop the double deserialise and the re-serialise)

On every hit the blob is deserialised in the validator, re-serialised to recompute an output
digest, and deserialised again by the caller. The re-serialisation is unnecessary because
`read_payload_bytes_validated` already computed and verified `payload_digest_for_bytes(bytes)
== manifest.payload_digest`, and `*_syntax_output_digest` is a pure function of that digest.
The second deserialisation is unnecessary because the validator already produced the value —
hand it out through the read outcome (`read_json_validated` already has this shape internally
and pays the same double cost; fix it once in `layer_cache.rs` and both adapters benefit).

- Impact (estimated from probes): plinty −341 ms (Go) −124 ms (TS) = **−0.47 s**; devloupe −514 ms −228 ms = **−0.74 s**. Larger once H1/H2 land, because it becomes ~17 % of devloupe's remaining warm wall.
- Risk: **medium-low.** The digest shortcut assumes `serde_json::to_vec(from_slice(bytes)) == bytes` for these payloads, which holds today (same serializer, no maps with unstable order) but is an invariant worth asserting rather than assuming. Safer variant: keep computing the digest, but from the *bytes* (`payload_digest_for_bytes`) rather than by re-serialising — that is unconditionally equivalent and still removes the `to_vec`.
- Verify: debug-assert the round-trip equality in tests; golden corpus; compare `output_digest` in the run report before/after on both repos.

### H5 — Make fact metadata cheap (or lazy) in `restore_file_facts`

`go.restore_db_inserts` + `ts.restore_db_inserts` is 701 ms (plinty) / 1 117 ms (devloupe)
warm, and is the largest remaining item after H1-H3. Per fact it builds 4-6 `String`s, takes
a global `Mutex` twice, sorts, and formats a hex digest into another `String`. Three
independent levers:

  a. **Intern without allocating**: give `StableKeyInterner` a `&str` lookup path and shard
     or `RwLock` the map so `intern`+`resolve` is one lock, not two.
  b. **Build stable-key text into a reused buffer** instead of a `Vec<(&str, String)>` per fact;
     avoid `fact.value.clone()` for string literals (borrow for hashing).
  c. **Compute metadata lazily** — only the facts a rule actually reads need a stable key or
     payload digest today; `fact_metadata_validation_enabled()` is off by default
     (`kernel.validate_fact_metadata` measured at 0.003 ms).
- Impact (estimated): (a)+(b) ~2-3× on this path → **−0.4 s plinty / −0.7 s devloupe**; (c) could remove nearly all of it but is a larger design change.
- Risk: (a)(b) **low** (pure refactor of a pure function); (c) **high** — fact metadata feeds `validate_fact_metadata` and the debug/JSON surfaces.
- Verify: `metadata_debug_json_for_test` snapshot equality; golden corpus; `polint facts` output diff.

### H6 — Don't recompute canonical provider projections that nothing consumes

`provider.digest.polint.go.syntax` and `provider.digest.polint.metrics` exist to produce a
provider-output identity for the run report. After H1 they cost 191 ms + 114 ms (plinty) and
280 ms + 296 ms (devloupe) — still 3 %-10 % of the *post-fix* warm wall. On a layer **hit**
the provider already returns an `output_digest` read straight from the manifest; the kernel
then throws it away for `go.syntax` and `metrics` and recomputes a canonical projection from
the whole DB anyway (`analysis_kernel/mod.rs`, the `match provider_id` block).

- Impact (estimated): **−0.30 s plinty, −0.58 s devloupe** by preferring the provider's own digest on a verified hit.
- Risk: **medium.** The canonical projection is also a *validation* of the restored DB (it returns `Err` on inconsistency, which downgrades the provider). Preserving that safety net means either keeping the projection behind a `--verify-cache` flag or proving the layer digest subsumes it.
- Verify: assert the recomputed digest equals the manifest digest on a corpus of fixtures before removing the recomputation; golden corpus; deliberately corrupt a blob and confirm the failure path still triggers.

### H7 — Parallelise the two remaining serial DB stages

`rule_execution_rows` is a trivially parallel `map` over rules (**[measured]** in the
prototype, though after H2 it is only ~30 ms so the parallelism is no longer the point).
More valuable: `fs::load_analysis_files_*` walks with a single-threaded `WalkBuilder` and
then pushes files into the DB sequentially (`fs.discover` 80-96 ms warm, but **429-743 ms
when the page cache is cold** — measured immediately after a compile). `WalkBuilder` has a
`build_parallel()` mode; the sort at the end already makes the result order-independent.

- Impact (estimated): `fs.discover` −60 % on a cold page cache (**−0.4 s** in that state), ~−50 ms warm.
- Risk: **low** — output is sorted by relative path before use, so walker order does not leak.
- Verify: assert discovered-file lists are identical between serial and parallel walkers over both repos; golden corpus.

### H8 — Skip `cargo run` when the rule-host artefact is already current

`run_local_rule_host_kind` (`cli/mod.rs:4252`) spawns `cargo run` unconditionally; prior art
measures the no-op at ~150 ms and this session measures the whole wrapper at 0.11 s / 0.47 s.
Fingerprint (rule sources + manifest + lockfile + `rustc -vV` + polint version), and on a
match exec the cached binary directly. This is item 3 of `research/code-preserving-rule-build/FINAL-REPORT.md`.

- Impact (estimated): **−0.15 s per run**, which is 5 % of plinty's post-fix 2.7 s and grows in relative terms as the analysis gets faster. Also removes cargo's ~230-fingerprint stat storm from the hot path.
- Risk: **medium** — a wrong fingerprint runs a stale rule host, which is a correctness bug with no diagnostic. Must include the resolved toolchain and every input cargo would have considered, and must fall back to `cargo run` on any doubt.
- Verify: mutate each fingerprint input in turn and assert a rebuild; assert byte-identical reports across `cargo run` and direct-exec paths.

### H9 — Stop writing the per-file `analysis/` store when the layer store covers it

The two stores hold the same facts: 47 MB + 42 MB (plinty), 71 MB + 89 MB (devloupe). The
per-file store is only read when the layer key misses. On a cold run it costs write time
inside `go.parse_all` / `ts.parse_all` and doubles cache footprint. Worse, the adapter reads
it back through `serde_json::Value` and re-serialises to bytes before the caller deserialises
into `CachedFileAnalysis` (`cache/analysis_cache_adapter.rs:33-69`) — three JSON passes per
file on the cold path.

- Impact (estimated): **cold −0.5 to −1.5 s** (part of plinty's 6.86 s `go.parse_all`), **cache size −45 %**. Keeping the per-file store but fixing the triple round-trip is the low-risk half.
- Risk: **medium** if removed (it is the only incremental path when a few files change and the whole-layer key misses — precisely the interactive edit loop, which these benchmarks do not exercise). **Low** for the round-trip fix alone.
- Verify: measure the single-file-edit scenario explicitly before changing the policy; golden corpus; `polint cache status` assertions.

### H10 — Attack the parse critical path on skewed repos (cold)

plinty parses 13.7 MB of Go in 6.86 s while devloupe parses 15 MB in 1.66 s. The difference
is file-size skew: one 558 KB file, top-10 files = 15 % of bytes and 21 % of facts. Rayon
schedules one file per task, so the tail file bounds the wall.

- Impact (estimated): **cold −2 to −4 s on plinty**, ~0 on devloupe. Options: chunk work below file granularity (hard with tree-sitter), or simply run the biggest files first (`par_iter` over a size-sorted list) so the long pole starts at t=0 — cheap and order-safe because results are keyed by path.
- Risk: **low** for the scheduling change (results are re-associated by path and the payload is sorted before hashing — confirm `parse_*_syntax_layer_payload` output order is normalised).
- Verify: `cmp` the layer blob bytes before/after on both repos; golden corpus.

### H11 — Include parser identity in the cache keys (correctness, not speed)

Fold `GO_PARSER_BACKEND` / `GO_PARSER_GRAMMAR` (and the Oxc equivalents) into
`go_syntax_layer_key`/`ts_syntax_layer_key`'s `toolchain_digest`, and add a version component
to `FileCacheKeyParts`. See §6.4 — I reproduced a silent 80-vs-93-function divergence at a
matching content hash purely by moving `tree-sitter` 0.26.8 → 0.26.13.

- Impact: **negative on wall time** (one extra cache generation on upgrade). Include it in the 10× work anyway, because every optimisation below relies on "same key ⇒ same facts" and that invariant is currently false.
- Risk: low; it only invalidates more.
- Verify: a test that bumping the constant changes the layer key.

### H12 — Free memory lazily / skip teardown

`check.teardown` is 92 ms (plinty) / 195 ms (devloupe) of pure `drop`, at the very end of a
process that is about to exit. `std::mem::forget` of the fact DB (or `std::process::exit`
after flushing stdout) reclaims it.

- Impact: **−0.09 s / −0.20 s**, i.e. 3.4 % of devloupe's post-fix wall.
- Risk: **medium** — must guarantee every buffered writer and cache file handle is flushed before exiting, and it makes leak detection in tests harder. Gate it to the CLI binary, never the library.
- Verify: assert stdout bytes and cache directory contents are unchanged; run under a fixture that writes the ai-friendly report and the semantic store.

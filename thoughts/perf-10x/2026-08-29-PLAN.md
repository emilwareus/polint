## 0. What we are optimizing and against what

Mission tier targets (R:601-608, 5× the 2026-08-28 baseline). Today's-machine baselines are
the ones the orchestrator captured at 01:01-01:13 (LOG.md) and are what quick-bench will
compare against:

| repo | tier | 2026-08-28 base | today's base (outer `polint check`) | target |
|---|---|---:|---:|---:|
| plinty | warm | 15.7 s | **13.99 s** | ≤ 3.1 s |
| plinty | cold | 25.1 s | **20.7 s** | ≤ 5.0 s |
| devloupe | warm | 11.2 s | **10.83 s** | ≤ 2.2 s |
| devloupe | cold | 13.1 s | **12.4 s** | ≤ 2.6 s |

**Honest projection up front.** Working through the measured decomposition (§1 per-wave
tables), the end state this plan reaches is:

| tier | projected end state | target | verdict |
|---|---:|---:|---|
| plinty warm | **1.5–1.9 s** (≈ 7–9×) | 3.1 s | **met, at wave 1** |
| devloupe warm | **2.4–2.8 s** (≈ 4×) | 2.2 s | **near miss** — `local/code-health-metrics` alone is a 1.70 s single-rule critical path (R:370, R:372) and no engine change gets under it |
| plinty cold | **5.5–8 s** (≈ 2.6–3.8×) | 5.0 s | **miss** — 6.86 s of it is tree-sitter parsing a skewed file set (R:213-217); H10 shaves the tail, it cannot remove the work |
| devloupe cold | **5.0–6.0 s** (≈ 2.1–2.5×) | 2.6 s | **miss** — same reason plus a metrics recompute |

Two of four targets are out of reach with **behaviour-preserving** changes in this budget.
The blockers are named, measured, and attributable — they are not "we ran out of ideas".
Reaching them needs work the mission explicitly excludes: a fact-snapshot protocol so the
prebuilt host produces facts without a per-repo engine build (R:437-441), and making
`local/code-health-metrics` itself cheaper, which is rule-pack code in a different repo.

## 1. Waves

Three waves, ordered by expected impact ÷ risk, with the constraint that **everything that
changes a cache key lands in wave 1** so waves 2 and 3 measure steady state.

Every hypothesis is **one atomic commit** so `git revert <sha>` is the rollback unit.

---

### Wave 1 — the two accidental quadratics, plus every key-changing change

Highest impact/risk ratio in the set: H1 and H2 are the measured 5.07× on plinty warm
(R:601-604) at "very low" and "low" risk, and both are pure-function memoizations. H3 and
H11 are folded in here **only because they change cache keys** — batching them with wave 1
buys exactly one invalidation for the whole mission.

Expected wave-1 exit: **plinty warm ≈ 2.8 s ✅, plinty cold ≈ 11.3 s, devloupe warm ≈ 4.5–5.0 s,
devloupe cold ≈ 6.7–7.8 s.** (Prototype direct-host numbers R:601-608 plus the wrapper
overhead of 0.11 s / 0.47 s from R:71-74, minus H3b's metrics-on-hit saving.)

#### H1 — memoize the per-file line count in `CanonicalGoSyntaxOutput::from_db`

- **Files:** `crates/polint/src/analysis_kernel/go_syntax_projection.rs`
- **Change:** add a per-`FileId` line-count memo to `GoContext` (struct at `:423`, built in
  `GoContext::new` at `:~410`). `canonical_span` (`:452`) takes the memoized count instead of
  calling `source.source.lines().count()` per fact. Prefer computing the whole memo eagerly in
  `GoContext::new` over a `RefCell` lazy map — the projection visits every owned file anyway,
  and an eager `BTreeMap<FileId, u32>` keeps `GoContext` immutable and `&self`-only, which is
  simpler than the prototype's interior mutability.
- **Expected impact [measured]:** `provider.digest.polint.go.syntax` **9 670 ms → 191 ms**
  on plinty (−68 % of warm wall) and **3 251 ms → 280 ms** on devloupe (R:456). Removes
  11.69 GB / 5.04 GB of re-scanned source per run (R:749-750). Identical saving on the cold
  tier — this cost is paid unconditionally, not on a miss (R:207-210).
- **Correctness:** `lines().count()` is a pure function of `source.source`, which is
  immutable for the life of the projection. **The prototype's
  `u32::try_from(...).unwrap_or(u32::MAX)` must NOT ship** — production must keep
  `map_err(|_| GoSyntaxProjectionError::Output)` so a >4 G-line file still errors instead of
  silently clamping.
- **Verify:** `cargo test --workspace`; `tests/golden.rs` + `tests/golden_corpus.rs`; the
  wave-1 byte-identity gate (§2.1) on all four (repo, tier) cells. Add a unit test asserting
  the projection over a multi-file fixture produces the same digest as a
  recompute-per-fact reference implementation.
- **Cache keys:** unchanged.

#### H2 — make `sdk::scope::glob_matches` allocation-free on the hot path

- **Files:** `crates/polint/src/sdk/scope.rs`
- **Change:** `glob_matches` (`:73`) currently calls `cached_matcher` (`:51`), which **clones**
  the memoized `GlobMatcher` on every call, then allocates `format!("./{value}")` for every
  non-match. Replace with: hold the `RwLock` read guard and match against `&GlobMatcher`
  borrowed from the map; build the `./`-prefixed variant into a reused `thread_local!`
  `String` buffer. Keep the public signature
  `pub fn glob_matches(pattern: &str, value: &str) -> bool` **exactly** — it is SDK surface.
  Write the miss path as an explicit insert-then-borrow, not the prototype's recursive
  self-call. If `cached_matcher` has no remaining callers, delete it; otherwise leave it.
  **Also correct its doc comment** (`:41-50`): the claim that "`GlobMatcher` clones are cheap
  (the inner regex is reference-counted)" is what this hypothesis disproves — the clone
  duplicates the inner `Glob`'s `String`s and costs 7.7–18.4 µs per (rule, file) (R:641).
- **Expected impact [measured]:** `run.rule_execution_rows` **1 635 → 32 ms** (plinty) and
  **1 539 → 30 ms** (devloupe); rule execution on devloupe **1 784 → 1 201 ms** because the
  same path is hit once per fact row from inside rules (R:466-468). ≈ −1.5 s on both repos,
  on **all four tiers** (R:186, R:196 show `rule_execution_rows` at full cost cold too).
- **Correctness:** same matcher instance, same call order, same `||` short-circuit, same
  substring fallback for invalid patterns. Add a proptest over the union of every
  `files` / `allow_files` pattern in `examples/**/.polint.toml` × every corpus path asserting
  `new(p, v) == old(p, v)`, including patterns that fail `Glob::new`.
- **Cache keys:** unchanged.
- **Explicitly not carried forward:** the prototype also ran `rule_execution_rows` under
  `rayon::par_iter` (diff hunk on `analysis_plan.rs:224`). After H2 that loop is 30 ms, so
  parallelism buys nothing and adds an ordering surface. **Drop it.** `rule_execution_rows`
  stays a sequential `.iter().map()` at `analysis_plan.rs:221`.

#### H3 — let the metrics layer manifest be readable, and stop making it enormous

Two coupled parts; land them in one commit.

- **Files:** `crates/polint/src/analysis_kernel/incremental/layer_cache.rs`,
  `crates/polint/src/metrics.rs`, `crates/polint/src/analysis_neutral/metrics.rs`
- **H3a — raise the ceiling.** `LAYER_CACHE_MANIFEST_MAX_BYTES` (`layer_cache.rs:26`) is
  4 MiB; devloupe's metrics manifest is **5 731 391 bytes** (R:312), so
  `read_file_to_string_with_limit` at `layer_cache.rs:302` errors, the manifest is evicted,
  and the layer misses **on every run, forever** (R:308-323). Raise it to
  `64 * 1_048_576` to match `LAYER_CACHE_PAYLOAD_MAX_BYTES` (`:27`). Second call site at
  `layer_cache.rs:~614` takes the same constant.
- **H3b — shrink the dependency edges.** `metrics_layer_dependency_edges`
  (`metrics.rs:137-165`) emits one `DependencyEdge` per source **and one per function**.
  Replace the per-function edge fan-out with a single `CacheNode::Input` edge carrying one
  digest over the sorted function digests. Same invalidation signal, ~10⁻⁴ the bytes.
- **Force one clean regeneration:** add a `"dependency-edges=v2"` component to
  `metrics_parameter_digest()` (`analysis_neutral/metrics.rs:150-160`). Without it the metrics
  layer key is unchanged by H3 (it derives from source + function digests, which H11 does not
  perturb), so devloupe's existing 5.73 MB manifest would be read back — now legal under the
  raised ceiling — and would linger until the next recompute. Bumping the parameter digest
  makes wave 1's first run rewrite it in compact form, deterministically.
- **Expected impact [measured]:** devloupe `provider.run.polint.metrics` **1 167 → ~660 ms**
  from the ceiling alone (`metrics.read_status` 2 → 1, R:479-483), and it stops rewriting
  20.6 MB blob + 5.7 MB manifest every run. With H3b the remaining read cost — dominated by
  parsing that 5.7 MB manifest — collapses too; prototype measured 514 ms of
  `metrics.read_layer` still standing after H3a alone (R:483), and R:628 shows metrics at
  **1 064 ms even on a hit**. Budget **−0.5 s (H3a) + −0.6 to −1.0 s (H3b)** on devloupe warm
  and cold. plinty does not request metrics (R:236) — expect ~0 there.
- **Correctness:** H3a only permits an already-digest-verified manifest to be read; the
  payload digest check at `layer_cache.rs:343-348` still gates the hit. H3b changes what is
  *written*, not what is *accepted* — old manifests still deserialize and canonicalize.
- **Verify:** a regression test that a layer whose manifest exceeds 4 MiB round-trips
  (write → read → `Hit`); a test that the metrics manifest for a fixture with N functions is
  O(sources), not O(sources + functions); `du -b .polint/cache/layers/manifests` on devloupe
  drops from ~6.4 MB to well under 1 MB after the first optimized run — this is the
  observable tell that H3 landed, since `metrics.read_status` is probe-only.
- **Cache keys:** **CHANGES.** The metrics layer key changes once; devloupe's 20.6 MB metrics
  blob + manifest are regenerated on the first optimized run. Accepted and stated.

#### H11 — put parser identity into the cache keys (correctness, not speed)

Included in wave 1 exactly as the mission recommends, and it belongs here on the merits:

1. It invalidates caches, so it must be batched with H3's invalidation rather than paid twice.
2. It only changes **invalidation** behaviour, never **output**. For any given run the facts
   are produced by the parser that is actually linked in; H11 changes which *previously
   cached* facts are considered reusable. The byte-identical constraint is on output, and
   output is unaffected: the wave-1 gate (§2.1) proves this by comparing the optimized
   run's stdout/JSON against the v0.3.0 capture on both warm and cold tiers.
3. Every later hypothesis in this plan relies on "same key ⇒ same facts", and **that
   invariant is currently false** (R:576-586). Research reproduced a silent 80-vs-93-function
   divergence at a matching content hash purely by moving `tree-sitter` 0.26.8 → 0.26.13,
   a 492-vs-493 diagnostic difference (R:333-338). Optimizing a cache whose keys under-
   specify its contents is optimizing on sand.

- **Files:** `crates/polint/src/go/adapter.rs` (`go_syntax_layer_key`, `:240`; `FileCacheKeyParts`
  construction at `:421`), `crates/polint/src/ts/adapter.rs` (`ts_syntax_layer_key`, `:247`),
  `crates/polint/src/analysis_api/cache_api.rs` (`FileCacheKeyParts`, `:9-17`),
  `crates/polint/src/analysis_kernel/go_syntax_projection.rs` (`:21-22`).
- **Change:**
  - Fold parser identity into `toolchain_digest`, which today carries only
    `env!("CARGO_PKG_VERSION")` (`go/adapter.rs:233-237`, `ts/adapter.rs:256-260`).
  - Go already declares its contract: `GO_PARSER_BACKEND = "tree-sitter-0.26.8"` and
    `GO_PARSER_GRAMMAR = "tree-sitter-go-0.25.0"` (`go_syntax_projection.rs:21-22`). **TS has
    no equivalent — introduce one** (`TS_PARSER_BACKEND = "oxc-0.129.0"`, sourced from the
    `[workspace.dependencies]` pin).
  - Add a parser/engine identity component to `FileCacheKeyParts` so the per-file
    `analysis/` store is keyed too — it carries **no version component at all** today
    (R:330-332).
  - **Layering:** `go_syntax_projection.rs` is a kernel module and `go/adapter.rs` is a
    frontend. Do not import kernel constants into the frontend — `tests/module_layering.rs`
    and `tests/internal_architecture.rs` will catch it. Define the constants where both
    layers may legitimately reach them (alongside the other frontend-visible contracts in
    `analysis_api` / `frontend_api`) and have `go_syntax_projection.rs` consume them from
    there, keeping `:103-104` and `:747-748` working.
- **Expected impact:** **negative on wall time**, once: one extra cache generation. Steady
  state after wave 1 is unchanged. This is deliberate (R:583-584).
- **Correctness / verify:** a test asserting that changing `GO_PARSER_BACKEND` or
  `GO_PARSER_GRAMMAR` changes `go_syntax_layer_key`, and the same for TS; a test asserting a
  changed identity component changes the `FileCacheKeyParts`-derived key. Add a **drift
  guard**: a test that reads the workspace `Cargo.lock` and asserts the resolved
  `tree-sitter` / `tree-sitter-go` / `oxc_parser` versions match the constants, so a
  `cargo update` inside this repo cannot silently desync them.
  - **Stated limitation:** this guards *this* repo. A downstream rule host that resolves a
    different patch version under a caret requirement is still not detected, because the
    constant is compiled in from polint's own tree. H11 closes the declared-vs-keyed gap and
    adds a local drift guard; it does not make the key parser-version-*derived*. Recording
    this honestly rather than overclaiming.
- **Cache keys:** **CHANGES.** Go and TS syntax layers and the entire per-file `analysis/`
  store are invalidated once — 88 MB (plinty) / 159 MB (devloupe) regenerated on the first
  optimized run (R:271-274). Accepted and stated.

Expected wave-2 exit: **plinty warm ≈ 1.8–1.9 s, plinty cold ≈ 7–9 s, devloupe warm ≈ 3.0–3.4 s,

#### H4 — read each layer blob once, and take the output digest from the manifest

The single cleanest win in the set: the code already computed the answer it then spends
341 ms / 514 ms re-deriving.

- **Files:** `crates/polint/src/go/adapter.rs`, `crates/polint/src/ts/adapter.rs`,
  `crates/polint/src/analysis_kernel/incremental/layer_cache.rs`
- **Change, part A — stop re-serializing to get the output digest.**
  `validate_syntax_layer_payload` (`go/adapter.rs:262-285`) ends with
  `output_digest == &go_syntax_output_digest_for_payload(payload)`, and
  `go_syntax_output_digest_for_payload` (`:398-404`) does a **full `serde_json::to_vec` of the
  31.7 MB / 45.3 MB payload** to recompute a digest. But:
  - the write path sets `output_digest = go_syntax_output_digest(&payload_digest)` where
    `payload_digest = payload_digest_for_json_bytes(payload_bytes)` (`:369-383`), and
  - the read path already computed `payload_digest_for_bytes(&payload_bytes)` and **rejected
    the entry unless it equals `manifest.payload_digest`** (`layer_cache.rs:339-348`) — this
    check runs *before* the validator is invoked (`:349`).

  Therefore `go_syntax_output_digest(&manifest.payload_digest) == manifest.output_digest`
  holds **by construction**, with no assumption about `to_vec(from_slice(b)) == b`. Pass the
  manifest's `payload_digest` through to the validator (the `AnalysisCache::read_layer_json`
  validator at `analysis_api/cache_api.rs:87-91` already receives
  `Option<&Digest>` for the output digest via `cache/analysis_cache_adapter.rs:78-80`; extend
  that hand-off to carry the payload digest too) and compute the comparison from it.
  This is **strictly better than the "safer variant" suggested at R:494** — no round-trip
  invariant is assumed at all.
- **Change, part B — stop deserializing twice.** The validator does
  `serde_json::from_slice::<SyntaxLayerPayload>(bytes)` (`go/adapter.rs:125`) and the `Hit`
  arm does it again on the same bytes (`:135-142`). Have the validator closure stash the
  parsed payload into a captured `Option<SyntaxLayerPayload>` (the closure is
  `&mut dyn FnMut`, so mutable capture works) and have the `Hit` arm `take()` it. No trait
  signature change, no public API change. `LayerCacheStore::read_json_validated`
  (`layer_cache.rs:239-275`) has the identical double-parse shape — fix it there once and the
  metrics layer benefits too.
- **Expected impact:** plinty **−341 ms (Go) −124 ms (TS) = −0.47 s**; devloupe
  **−514 ms −228 ms = −0.74 s** (R:290-296, R:491-492). Warm tier only — on a miss the layer
  is not read at all.
- **Correctness / verify:** debug-assert in tests that
  `go_syntax_output_digest(&manifest.payload_digest) == go_syntax_output_digest_for_payload(&payload)`
  on a written-then-read fixture, for both Go and TS; a test that a corrupted blob still
  produces `InvalidEvicted` (the payload-digest gate at `layer_cache.rs:343` must still fire);
  compare the `output_digest` recorded in the run report before/after on both benchmark repos.
- **Cache keys:** unchanged. The digest *values* are provably identical, so existing caches
  stay valid.

#### H5 — make fact metadata construction cheap in `restore_file_facts`

Largest remaining single item after H1-H4: `go.restore_db_inserts` + `ts.restore_db_inserts`
= 701 ms (plinty) / 1 117 ms (devloupe) warm, and it is paid on the cold tier too
(`go.restore` 513 / 703 ms, R:190, R:196).

- **Files:** `crates/polint/src/internal_core/stable_key.rs`, `crates/polint/src/core/db.rs`
- **Change (a) — one lock, no allocation, on the interner fast path.**
  `StableKeyInterner::intern` (`stable_key.rs:37`) takes `impl Into<String>` — forcing an
  allocation before the lookup — then `resolve` (`:54`) takes the `Mutex` a *second* time.
  Every `push_*` does both (`db.rs:715-760`). Change to: `RwLock<StableKeyInternerState>` with
  a `&str` read-path lookup that allocates nothing on a hit, plus an
  `intern_and_resolve(&str) -> (StableKeyId, Arc<str>)` so the pair is one lock acquisition.
  - **Hard constraint:** `StableKeyId(u32)` indexes `state.keys: Vec<Arc<str>>`
    (`stable_key.rs:26-29`, resolve at `:54-62`). **Do not shard the map** — sharding breaks
    the dense-index invariant and changes id assignment. Ids must remain assigned in exactly
    the same insertion order, which the sequential `restore_file_facts` loop
    (`db.rs:3682-3730`) guarantees.
  - Keep new methods `pub(crate)` unless an existing `pub` neighbour makes that impossible;
    `internal_core` is `pub(crate)` (`lib.rs:45`) so nothing here is public API, but
    `unreachable_pub` is on and CONVENTIONS.md requires the narrowest visibility that works.
- **Change (b) — build stable-key text into a reused buffer.** `*_metadata` (e.g.
  `function_metadata`, `db.rs:3798-3825`) builds a `Vec<(&str, String)>` with 4-6 fresh
  `String`s per fact: `path_for(fact.file)` clones the relative path,
  `language_label(...).to_string()`, `fact.name.clone()`, `span_metadata_value(...)`, and for
  string literals `fact.value.clone()` — the entire literal text. Format into a
  caller-owned reusable buffer and hash from `&str`; borrow the literal value instead of
  cloning it.
- **Not doing (c).** Lazy metadata (R:509-511) would remove nearly all of this but is a
  design change rated **high** risk against the debug/JSON surfaces. Out of scope for a
  byte-identical pass.
- **Expected impact:** ~2–3× on this path → **−0.4 s plinty / −0.7 s devloupe** warm
  (R:512), with a comparable share on cold.
- **Correctness / verify:** the **stable-key text must be byte-identical** — it is hashed
  into a digest that can reach the report. Gate on `metadata_debug_json_for_test` snapshot
  equality, a `polint facts` output diff on a fixture, and a test asserting id assignment
  order is unchanged for a fixed fact sequence. Then the §2.1 gate.
- **Cache keys:** unchanged (metadata is not part of any key; the payload digests are over
  the serialized layer, not over `FactMeta`).

#### H10 — parse the biggest files first

The only change that materially moves plinty cold. plinty parses 13.7 MB of Go in 6.86 s
while devloupe parses 15 MB in 1.66 s; the difference is file-size skew — one 558 KB
generated file, top-10 files = 15 % of bytes and 21 % of facts, and rayon schedules one file
per task so the tail file bounds the wall (R:213-217, R:566-570).

- **Files:** `crates/polint/src/go/adapter.rs` (`parse_go_syntax_layer_payload`, `:286-305`),
  `crates/polint/src/ts/adapter.rs` (the corresponding `parse_ts_syntax_layer_payload`)
- **Change:** before `files.par_iter()`, iterate a size-descending index order so the long
  pole starts at t=0. Do **not** reorder the output — collect results and re-associate by
  index/path so `payload.files` keeps its existing order.
- **Expected impact:** plinty cold **−2 to −4 s**, devloupe ~0 (R:572).
- **Correctness / verify:** `cmp` the layer blob bytes before/after on both benchmark repos —
  this is the sharp test, because the blob's byte order is exactly what must not change.
  Confirm `parse_*_syntax_layer_payload` normalises output order before hashing (R:574).
  Then the §2.1 gate on the cold tier.
- **Cache keys:** unchanged, **provided the blob bytes are identical** — which the `cmp`
  above proves. If the blob bytes differ, H10 is reverted (§4).

#### H12 — don't drop the fact DB on the way out

- **Files:** `crates/polint/src/runner/mod.rs`
- **Change:** `check.teardown` is 92 ms (plinty) / 195 ms (devloupe) of pure `drop` at the end
  of a process that is about to exit (R:587-597). Use **`std::mem::forget` on the fact DB**,
  not `std::process::exit` — this reclaims the dominant cost while leaving every other
  `Drop` impl (writers, cache handles, temp dirs) to run normally. That is strictly safer
  than the `process::exit` variant research floated.
- **Placement:** in the CLI entry path in `runner::run_cli` only, at the point where the
  report has been rendered and printed. **Never in a library helper** — the rule host links
  `polint::runner`, and any code path that continues after the call must still free.
- **Expected impact:** **−0.09 s plinty / −0.20 s devloupe**, all tiers; ~3.4 % of devloupe's
  post-fix wall (R:594-595).
- **Correctness / verify:** before implementing, audit the `AnalysisDb` type graph for any
  side-effectful `Drop` (cache flush, temp-file cleanup, semantic-store write). If one
  exists, H12 is dropped. Then: assert stdout bytes unchanged; assert
  `find .polint/cache -type f | sort | xargs md5sum` is identical before/after on a fixture
  that writes the ai-friendly report and the semantic store; run the CLI integration tests
  (`tests/cli.rs`) which assert exit codes and output.
- **Cache keys:** unchanged.

### Wave 3 — the last warm crumbs and the cold-path round-trip

Smaller, and deliberately last: H6 carries the only "medium" correctness risk among the
non-optional items, and H9-lite is cold-tier-only. Both are cut without argument if the
07:45 UTC code freeze (§6) arrives first.

Expected wave-3 exit: **plinty warm ≈ 1.5–1.6 s, plinty cold ≈ 5.5–8 s,
devloupe warm ≈ 2.4–2.8 s, devloupe cold ≈ 5.0–6.0 s.**

#### H6 — prefer the provider's verified digest over recomputing the canonical projection

- **Files:** `crates/polint/src/analysis_kernel/mod.rs` (the `match provider_id` block at
  `:252-271`)
- **Change:** on a layer **hit** the provider already returns an `output_digest` read straight
  from the manifest, and the kernel throws it away for `polint.go.syntax` and `polint.metrics`
  and recomputes a canonical projection from the whole DB
  (`CanonicalGoSyntaxOutput::from_db` at `:259`, `CanonicalMetricsOutput::from_db` at `:267`).
  Prefer the provider's digest when the provider reported a verified reuse.
- **Expected impact:** **−0.30 s plinty, −0.58 s devloupe** (R:526). After H1 these
  projections cost 191 + 114 ms (plinty) and 280 + 296 ms (devloupe) — 3–10 % of the
  *post-fix* warm wall (R:520-521).
- **Risk — medium, and the safety net matters.** The projection is also a *validation* of the
  restored DB: it returns `Err` on inconsistency, which downgrades the provider (R:527-528).
  Keep that net by only taking the shortcut on `LayerCacheReadStatus::Hit` with
  `record_verified_reuse()` already set (`go/adapter.rs:133-134`), where the payload digest
  has been checked against the manifest (`layer_cache.rs:343`) and the validator has confirmed
  the file/content-hash set matches (`go/adapter.rs:270-284`). On any other status, recompute.
- **Correctness / verify — this is a hard pre-flight gate.** Before removing anything, add a
  test-only assertion that the recomputed projection digest **equals** the manifest digest
  across the fixture corpus and on both benchmark repos. If it ever differs, **H6 is dropped,
  not debugged** (§4). Then: deliberately corrupt a blob and confirm the failure path still
  triggers; `cmp` the inner JSON report (which carries `provider_outputs` identity records) —
  this is the sharpest of all the byte-identity checks and the reason §2.1 gates on the JSON,
  not just the human render.
- **Cache keys:** unchanged.

#### H9-lite — kill the triple JSON round-trip in the per-file cache adapter

- **Files:** `crates/polint/src/cache/analysis_cache_adapter.rs` (`:33-69`)
- **Change:** the adapter reads the per-file store back through `serde_json::Value` and
  re-serialises to bytes before the caller deserialises into `CachedFileAnalysis` — **three
  JSON passes per file** on the cold path (R:557-560, R:643). Read and hand out bytes
  directly.
- **Explicitly NOT doing the rest of H9.** Removing the per-file `analysis/` store entirely
  is rated medium risk because it is the only incremental path when a few files change and
  the whole-layer key misses — the interactive edit loop, which these benchmarks do not
  exercise (R:563-564). Changing a policy the benchmark cannot measure, on the strength of a
  benchmark, is exactly the wrong trade.
- **Expected impact:** cold only, **−0.5 to −1.5 s** on plinty as part of its 6.86 s
  `go.parse_all` (R:562). Upside here may exceed the estimate: plinty writes 47 MB across
  2 764 files inside `go.parse_all`, and 2 MB/s of tree-sitter throughput is anomalously slow
  for the parser alone — some of that 6.86 s is this round-trip. Measure it.
- **Correctness / verify:** `polint cache status` assertions; a fixture round-trip test
  (write → read → identical `CachedFileAnalysis`); the §2.1 cold-tier gate.
- **Cache keys:** unchanged (the on-disk JSON is byte-identical; only the in-process path
  changes).

#### H7 — parallel file discovery *(optional, cheap)*

- **Files:** `crates/polint/src/fs/mod.rs` (`discover_files_scoped`, `:38-60`)
- **Change:** `WalkBuilder::build()` (`:46-52`) is single-threaded; switch to
  `build_parallel()`. The result is sorted by relative path before use, so walker order does
  not leak (R:539).
- **Expected impact — and a harness caveat that decides its priority.** Research measures
  `fs.discover` at 80–96 ms warm but **429–743 ms when the page cache is cold** (R:536-537).
  **The bench harness never drops the page cache** — `quick-bench.sh` and `run-bench.sh` call
  `sync` but not `drop_caches`. So H7's real win is **not measurable on this harness**; expect
  only **~−50 ms** to show up. Land it for the correctness-free win, do not expect it to move
  a number, and do not claim the cold-page-cache figure in the final report.
- **Correctness / verify:** assert discovered-file lists are identical between serial and
  parallel walkers over both benchmark repos.
- **Cache keys:** unchanged.

#### H8 — skip `cargo run` when the rule host is current *(conditional; recommend cutting)*

- **Files:** `crates/polint/src/cli/mod.rs` (`run_local_rule_host_kind`, `:4252`)
- **Why it is conditional, and probably out:**
  1. **It is not measurable on the current harness.** H8 lives in the **outer** binary. The
     bench protocol runs the released v0.3.0 binary as the outer `polint` and only builds the
     **inner rule host** from the worktree via `POLINT_CARGO=.../cargo-polint-local`
     (`quick-bench.sh:5` defaults `POLINT_BIN` to `/workspace/bench-polint-results/bin/polint`).
     Every other hypothesis in this plan is inner-host code and is measured. H8 is not.
     Measuring it means swapping the outer binary for a worktree build, which changes the
     renderer that produces the very bytes §2.1 compares — a bad trade this late.
  2. **It carries the only silent-correctness risk in the set.** A wrong fingerprint runs a
     stale rule host and reports wrong diagnostics with no error (R:551).
  3. **Its win is at the noise floor.** −0.15 s (R:549) against an outer-binary run-to-run
     spread of 13.52–14.34 s today (R:717), which will not shrink proportionally.
- **If time genuinely allows** (wave 3 core complete and verified before 07:15 UTC): implement
  it fingerprinting rule sources + manifest + lockfile + `rustc -vV` + polint version, falling
  back to `cargo run` on **any** doubt, and verify by mutating each fingerprint input in turn
  and asserting a rebuild, plus asserting byte-identical reports across the `cargo run` and
  direct-exec paths. Report its effect from a **separate** two-binary A/B (worktree-built
  outer vs released outer, same rule host), never folded into the headline benchmark.
- **Recommendation: cut it.** Note it in the final report as identified, scoped, and
  deliberately deferred, with the reasoning above.

## 2. Correctness constraints

These are gates, not aspirations. A wave is not "done" until all of §2.1–§2.5 pass.

### 2.1 Byte-identical output vs the released v0.3.0 binary

**Capture the baselines before the first line of code changes.** For each repo × tier, from
the released binary, into `/tmp/perf10x/base/`:

- **Outer stdout:** `polint check --fail-on none` under the harness env, captured per tier.
- **Inner JSON report:** the rule host invoked directly —
  `<host> check --format json --fail-on none --ignore-comments true --kind check` (R:667-671).
  **This is the gating artifact.** The human render is a projection of it, and the JSON is
  what carries `provider_outputs` identity records — the only surface H6 could perturb.

After each wave, regenerate both artifacts under the **same cache provenance** and `cmp`.

**Provenance rules (R:341-345 — never compare warm to cold):**

- warm(v0.3.0, warm cache) **vs** warm(optimized, warm cache)
- cold(v0.3.0, empty cache) **vs** cold(optimized, empty cache)
- After wave 1's key change the optimized warm cache is a *regenerated* cache. That is still
  a legitimate warm-vs-warm comparison — both sides are steady-state layer hits — and the
  fact that output is byte-identical across the two provenances is precisely the evidence
  that H11 changed invalidation and not results.
- Back up both repos' `.polint/cache` before starting and restore on any abort, exactly as
  research did (R:685-689).

**Any single byte of difference on any cell blocks the wave.**

### 2.2 Test suite

```
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
cargo test --workspace
```

Run with `export PATH="/opt/data/home/.local/bin:$PATH"` so the Go 1.27.0 toolchain is on
`PATH` for the sidecar tests.

**Pre-existing Go-sidecar failures are tolerated only if proven pre-existing.** Before wave 1,
capture the base-commit failure set:

```
git stash -u && cargo test --workspace 2>&1 | tee /tmp/perf10x/tests-base.txt ; git stash pop
```

Extract the set of failing test names. After each wave, extract the same set and require
**set equality**. Any new name in the set is a wave abort (§4). A test that starts *passing*
is fine, but note it.

### 2.3 No public API change

The supported surface is `polint::sdk` (incl. `prelude`, `scope`) and `polint::runner`
(AGENTS.md conventions block). Everything this plan touches is behind `pub(crate)` modules
(`lib.rs:19-59`) **except** `sdk::scope::glob_matches` (H2), whose signature is preserved
verbatim. Gate on `tests/public_surface_leak.rs`, `tests/consumer_api_compat.rs`,
`tests/internal_architecture.rs`, `tests/module_layering.rs`.

### 2.4 Visibility and comment discipline

- CONVENTIONS.md: narrowest visibility that works — `private` → `pub(super)`/`pub(in path)` →
  `pub(crate)` → `pub` only across an intentional boundary. New helpers default to private;
  cross-module helpers get `pub(crate)`. `unreachable_pub` is on: if it fires, **fix
  visibility**, never weaken the lint.
- AGENTS.md shipped-code comment policy: **no GSD/phase/plan/task/milestone references** in
  any source comment, doc comment, test, fixture, lint-suppression reason, build file, or
  CI name. Comments explain enduring behaviour and invariants in domain terms. Describe
  sequencing as steps or stages, never as delivery phases. Do not write "wave 1", "H3", or
  "perf-10x" into the code — those live here, in commit messages, and in the PR.
- Do write the *invariants* down where they are load-bearing: why the interner must stay
  densely indexed (H5a), why `go_syntax_output_digest(&manifest.payload_digest)` is exact
  (H4), why the parser identity constants must track the lockfile (H11).

### 2.5 Unconditional, and no scaffolding

- **The `POLINT_PERF_FIX` env gate must not exist in shipped code.** Behaviour-preserving perf
  work never ships behind an env flag — an optimization you can turn off is an optimization
  you have to test twice and a code path users can accidentally take.
- **`crates/polint/src/perf_probe.rs` must not be committed**, nor any `perf_probe::` call,
  `Probe::new`, `note(...)`, `SPAN_CALLS`/`SPAN_BYTES` counter, or `TEMPORARY (research
  prototype)` comment from the prototype diff.
- The prototype diff is a **reference for the mechanism**, not a patch to apply. Its
  `layer_cache.rs` env-switched ceiling function, its `RefCell` line-count memo, its recursive
  `glob_matches_borrowed`, its `unwrap_or(u32::MAX)`, and its rayon `rule_execution_rows` are
  all deliberately superseded above.
- Before opening the PR: `git diff 13e53f35 -- crates/ | grep -niE 'perf_probe|POLINT_PERF|TEMPORARY|phase [0-9]|GSD'` must be empty.

## 3. Benchmark integration — what this plan expects of the orchestrator

The orchestrator owns the runs; the plan states the contract.

**Harness invariants (LOG.md 02:05-02:45):**

```

```

Rule hosts then build from the worktree with vendored `--locked` deps (no resolution drift),
validated byte-identical to the released v0.3.0 host on both repos.
**After every bench invocation, restore both packs' lockfiles** — patched resolution rewrites
them and they are tracked files: `git -C /workspace/benchmark-plinty checkout -- .polint/rules/Cargo.lock`
(and the same for devloupe).

**Between waves:** `bash /workspace/bench-polint-results/quick-bench.sh`.
**At the end:** `bash /workspace/bench-polint-results/run-bench.sh`.

**Reading quick-bench output:**

- Order per repo is `warm-1, warm-2, cold-1, cold-2`.
- **warm-1 is a warmup datapoint, warm-2 is the measurement.** warm-1 pays the rule-host
  rebuild (~105 s per repo for a polint-only rebuild, R:400-401; ~2–4 min if more of the
  dep closure is touched).
- **`quick-results.tsv` is truncated on every invocation** (`quick-bench.sh` rewrites the
  header). Copy it aside between waves:
  `cp quick-results.tsv /workspace/bench-polint-results/quick-results-wave<N>.tsv`.
  `run-bench.sh` likewise truncates `raw-results.tsv`.

**Cache-key changes — wave 1 only.** H3 and H11 change keys, so the **first** optimized run
after wave 1 pays a full cold rebuild of the analysis cache (88 MB plinty / 159 MB devloupe,
R:271-274) even in the `warm` tier, which does not delete `.polint/cache`. In practice
warm-1 absorbs it — it is already the discarded warmup. **warm-2 is steady state and is the
number.** If warm-2 still looks anomalous, re-run quick-bench once before drawing a
conclusion.
**Waves 2 and 3 change no keys**, so their warm-1 hits the existing cache and their warm-2 is
steady state directly. Editing polint source does *not* by itself invalidate anything:
`provider_version` is `env!("CARGO_PKG_VERSION")` = 0.3.0 and is untouched by this work
(`go/adapter.rs:233-237`).

**Observable tell that H3 landed:** `du -b /workspace/benchmark-devloupe/.polint/cache/layers/manifests`
drops from ~6.4 MB to well under 1 MB. `metrics.read_status` is probe-only and probes are not
shipping.

**Ice-cold tier caveat for the final report.** `run-bench.sh` runs three ice-cold iterations
per repo, each deleting `CARGO_HOME` and the target dir. Under the patch harness those builds
resolve from the **vendor directory** instead of fetching from crates.io — and for plinty,
instead of cloning the 222 MB polint git repo (R:390-392). Ice-cold numbers will therefore

speedup on that tier**, and note separately that recommending `polint = "0.3.0"` over a git

**Ordering hazard:** `run-bench.sh` **deletes both repos' `.polint/cache` and both
`/tmp/bpol-*` directories when it finishes.** Every byte-identity check in §2.1 must be
complete before it starts, or the warm baselines are gone.

## 4. Abort and rollback criteria

Each hypothesis is one commit. Rollback is `git revert <sha>` of that commit alone; the rest
of the wave stands.

**Immediate revert of the responsible commit, any wave:**

| trigger | action |
|---|---|
| Any byte difference in the inner JSON report or outer stdout, any (repo, tier) | Revert. Bisect the wave commit-by-commit against the §2.1 gate. Do not proceed to the next wave until clean. |
| A test name in the failing set that is not in the base-commit set (§2.2) | Revert. |
| `cargo fmt` / `clippy -D warnings` failure | Fix in place — not a wave abort — unless the fix requires weakening a lint, in which case revert. |
| Public-surface or module-layering test fails | Revert; the change crossed a boundary CONVENTIONS.md forbids. |
| warm-2 median for either repo is **> 3 % worse** than the previous wave's warm-2 | Bisect the wave; revert the offending hypothesis, keep the rest. 3 % is above the ~1–2 % run-to-run spread research measured on direct host runs (R:713-728) while staying tight enough to catch a real regression at 2 s scale. |
| cold-2 median for either repo is **> 5 % worse** than the previous wave's cold-2 | Same. Wider band because the cold tier's spread is genuinely larger (plinty cold 19.97–24.16 s, R:721). |

**Hypothesis-specific aborts:**

- **H3** — if raising the ceiling does not shrink the devloupe manifest directory after the
  first optimized run, H3b did not take effect: investigate before benching, do not report a
  number.
- **H4** — if the debug-assert `go_syntax_output_digest(&manifest.payload_digest) ==
  go_syntax_output_digest_for_payload(&payload)` ever fires, revert immediately; the
  by-construction argument is wrong and the whole hypothesis is void.
- **H5** — if `metadata_debug_json_for_test` snapshots or `polint facts` output differ by one
  byte, revert. Stable-key text is not negotiable.
- **H6** — if the recomputed projection digest ≠ the manifest digest on **any** fixture in
  the pre-flight assertion, **drop H6 entirely.** Do not debug it under time pressure; it is
  a 0.3–0.6 s hypothesis guarding a validation path.
- **H10** — if the layer blob bytes differ before/after, revert. Parse order must not be
  observable.
- **H12** — if any `Drop` impl in the `AnalysisDb` type graph is side-effectful, or if the
  cache directory checksum differs after a run, revert.
- **H8** — if any fingerprint-mutation test fails to trigger a rebuild, revert. A stale rule
  host is a silent wrong answer.

**Wave-level abort:** if a wave cannot be made clean within 45 minutes of its verification
starting, revert the entire wave to the previous wave's tip and continue to the next wave.
The plan is designed so each wave stands alone.
